# Парсер Telegram-каналов — карта проекта

Этот файл нужен, чтобы вернуться в работу после перерыва: что уже сделано,
что осталось, какие решения приняты и где закопаны грабли.
Читать перед тем, как предлагать что-то менять.

## Что это

Настольная программа на PySide6. Читает Telegram-каналы, показывает каждый
новый пост локальной модели в LM Studio и пересылает отобранное в приватный
канал. Пользователь — журналист, не программист: всё настраивается в окне,
никаких файлов и командной строки.

## Где что лежит

| Файл | За что отвечает |
|---|---|
| `core/settings.py` | чтение и запись настроек, `blockers()`, `problems()` |
| `core/paths.py` | ЕДИНСТВЕННОЕ место, знающее пути. Никто больше их не собирает |
| `core/secrets.py` | секреты в Диспетчере учётных данных Windows |
| `core/llm.py` | обращение к модели, `probe()` для проверки |
| `core/schedule.py` | ЕДИНСТВЕННОЕ место, знающее про планировщик Windows |
| `core/lmstudio.py` | ЕДИНСТВЕННОЕ место, знающее про команду `lms` |
| `core/lastrun.py` | отметка «проверка идёт»: по ней виден оборванный прогон |
| `core/telegram.py` | отправка отчёта ботом |
| `core/proxy.py` | ЕДИНСТВЕННОЕ место, знающее про прокси. Адрес берётся у Windows |
| `core/logs.py` | журнал на loguru, зеркало print, перехват падений |
| `digest/digest.py` | сама проверка каналов. Логика отбора и состояния |
| `digest/app.py` | главное окно, страницы, замок на один экземпляр |
| `digest/ui.py` | язык оформления: цвета, карточки, кнопки, шрифты |
| `digest/runner.py` | поток проверки, лок, отчёт после закрытия цикла, запуск сео-поиска |
| `topic_finder/topic_finder.py` | сео-поиск: запросы через Bukvarix, отбор тем моделью. Свой репозиторий |
| `digest/tgclient.py` | поток Telegram: вход, канал доставки, проверка ссылок |
| `digest/wizard.py` | страница «Вход в Telegram»: ключи доступа, номер, код |
| `digest/channels_window.py` | таблица каналов: ссылка, ник, название, состояние |
| `digest/console.py` | журнал с посимвольной печатью («Матрица») |
| `digest/schedule_window.py` | страница «Расписание»: время, дни, что будет |
| `digest/about.py` | страница «О программе», ссылки в `LINKS` |
| `digest/sandbox.py` | песочница для проверки входа, не трогая боевые файлы |
| `build.py` | сборка одной командой: программа, инструмент рядом, проверки |
| `installer.iss` | установщик Inno Setup |
| `README.md` | лицо проекта на GitHub: что это, требования, установка, сборка |
| `LICENSE` | MIT |

Личное, вне репозитория: `CLAUDE.md`, `.claude/`, `topic_finder/`,
`daily_guard.py`, `diag.py`, батники. В репозитории едут только шаблоны:
`settings.default.json` и `interests.default.txt`.

У `topic_finder/` **свой отдельный репозиторий** прямо в папке, без адреса на
GitHub. Родительский `.gitignore` прячет эту папку целиком, поэтому утечь
физически некуда — это разные хранилища. Ветки для той же цели не годятся:
у публичного репозитория публичны ВСЕ ветки, и защита держалась бы только
на внимательности при каждом `push`.

Рабочие файлы автора (`settings.json`, `interests.txt`, состояние, сессия,
данные сео-поиска) лежат не в папке проекта, а в `%LOCALAPPDATA%\TelegramDigest`
— см. «Портативный режим у автора выключен».

## Что сделано

1. Настройки вынесены из кода в `settings.json` и `interests.txt`.
2. Пути через `core/paths.py`, блокировка на portalocker.
3. Журнал на loguru: работает без консоли, хранит 30 дней, ловит падения.
4. Адрес и имя модели из настроек, ключ для облачных адресов.
5. Окно PySide6: страницы вместо всплывающих окон, боковое меню.
6. Вход в Telegram: номер, код, пароль 2FA, создание канала доставки.
7. Экраны настроек, каналов, интересов.
8. Проверка запускается из окна: прогресс, счётчики, остановка.
9. Секреты в Диспетчере учётных данных Windows.
10. Сборка PyInstaller `--onedir`, иконка, установщик Inno Setup.
11. Внешний вид: тема, размер букв, «Матрица», кликабельные ссылки.
12. Расписание: задача в Планировщике Windows, ключ `--run-now`.
13. LM Studio поднимается сам перед проверкой и освобождает память после.
14. Ошибки настроек написаны по-русски и говорят, в какой раздел окна идти.
15. Ключи доступа (api_id, api_hash) — на странице входа, пока не вошли.
16. Оборванная проверка: память освобождается, человеку об этом сказано.
17. В таблице каналов виден столбец с названиями.
18. `README.md` и `LICENSE` — проект готов к публикации.
19. Опубликован на GitHub, адрес репозитория стоит в «О программе».
20. Сео-поиск запускается из программы сразу после проверки постов —
    пятый шаг старого `run_all.bat` переехал в окно.
21. Данные сео-поиска живут рядом с данными дайджеста и переезжают туда сами.
22. Портативный режим у автора выключен: всё работает с одной папкой данных.
23. Про доступ к Telegram сказано прямо: раздел «Доступ к Telegram»
    в `README.md` и строка про VPN в самой ошибке подключения.
24. Прокси: чтение каналов идёт через тот же прокси, что указан
    в настройках Windows. До этого посты не читались вовсе там, где
    Telegram работает только через обход.

Версия `1.0` собрана и проверена на живой машине: и программа, и установщик.
Последний выложенный релиз — **`v1.3`** (24 августа 2026), заголовок
«программа берёт прокси из настроек Windows». Код на GitHub и выложенный
установщик сошлись: догонять нечего.

## Что делаем дальше

Список на ближайшее, в порядке срочности.

1. **Ошибка: «Не указано, куда пересылать отобранные посты» не исчезает.**
   Надпись остаётся даже после того, как программа сама завела канал
   доставки и подставила его в поле — то есть претензия уже не по делу.
   Где искать: строку рождает `blockers()` в `core/settings.py` (около
   строки 424), когда пусто `telegram.target`. Значит после успешного
   `channel_created` либо не перечитываются настройки
   (`settings.load(force=True)`), либо не пересчитывается сам список
   претензий на странице. Проверять на чистой установке: у автора поле
   давно заполнено, и ошибка не воспроизведётся.

2. **Токен бота утекает в журнал.** `core/telegram.py`, строки 77 и 97:
   ошибка выводится как есть, а `requests` кладёт в её текст весь адрес
   запроса — вместе с токеном. Кто получит файл журнала, получит и бота.
   Чинится вырезанием токена из текста перед записью. Автор решил свой
   токен не отзывать (он только на его машине), но саму дыру закрыть надо:
   у коллег журналы будут уезжать в переписку при первой же жалобе.

3. **Сообщение об обрыве врёт.** Когда проверка срывается, человек видит:
   «Проверка прервалась: <английский текст ошибки>. Отобранное до этого уже
   отправлено, остальное дочитается в следующий раз». Обе половины плохи.
   Первая: «отобранное уже отправлено» — неправда, если проверка упала
   на подключении, до первого канала. Отправлять было нечего. Вторая:
   человеку показывают английскую строку из внутренностей библиотеки,
   из которой не понять ни что случилось, ни что делать.

   Нужный текст в программе УЖЕ ЕСТЬ: `human_error` в `digest/tgclient.py`
   (около строки 100) говорит именно то, что надо — «Не удалось связаться
   с Telegram. Проверьте интернет и VPN: если Telegram не открывается у вас
   на этом компьютере, программа тоже до него не достучится». Но пользуется
   им только экран входа. Прогон ловит всё общим `except` в
   `digest/runner.py` (около строки 138) и до этого текста не добирается.

   Поймано 24 августа 2026 на живом обрыве: шесть дней подряд человек видел
   именно это сообщение и понять из него, что дело в прокси, не мог.

4. **Запуск по расписанию: три жалобы от 5 августа 2026, разобраны 24 августа.**
   Две сняты, одна осталась. Всё, что ниже, померено по журналам программы
   и по `schtasks`, а не выведено рассуждением.

   - **«Расписание умерло совсем» — НЕ ПОДТВЕРДИЛОСЬ.** Задача жива: включена,
     состояние «Готово», прошлый результат `0`, путь к программе верный.
     С 5 августа она приходила двенадцать раз: 5, 10, 11, 12, 14, 17, 18, 20,
     21, 22, 23 и 24 августа. Жалоба была верна на тот день, когда её записали:
     с 6 по 9 августа задача и правда молчала четыре дня подряд. С 10-го пошла
     сама. Почему замолкала и почему заговорила — не установлено и уже не
     установить: журнал Планировщика Windows выключен (это его состояние
     по умолчанию), истории событий нет. Задачу при этом никто не пересоздавал:
     в ней стоит дата начала 5 августа, а `core/schedule.py` пишет туда день
     создания.

   - **Запуска в 10:00 не бывает вовсе — и это важнее всего остального.**
     Ни один из двенадцати запусков не случился в назначенный час. Все
     двенадцать догоняющие: 12:12, 14:52, 14:54, 15:17, 15:01, 13:02, 11:58,
     14:15, 12:44, 11:53, 13:01, 11:18. Компьютер в десять утра выключен,
     и проверка приходит через минуту-другую после того, как его включают.
     То есть `StartWhenAvailable` у автора не запасной путь, а ЕДИНСТВЕННЫЙ
     рабочий режим, каждый день. Отсюда следствие, которого раньше не видели:
     обход блокировки должен быть поднят к моменту ВКЛЮЧЕНИЯ компьютера,
     а не к десяти утра. Поднимается руками — проверка успеет сорваться.

   - **Долгий старт — ПОМЕРЕН.** От срабатывания задачи до первого канала
     проходит около 55 секунд, и держится это ровно: 18, 22, 23 и 24 августа —
     54, 56, 56 и 55 с. Раскладка: 3 с планировщик поднимает программу,
     7–18 с программа собирает окно и доходит до решения «иду проверять»,
     38–46 с грузится модель в LM Studio. Четыре пятых времени — это `lms load`
     на восьмимиллиардной модели, то есть подозреваемый номер три из трёх.
     Ускорять программу незачем: на неё приходится от силы четверть минуты,
     и часть её уходит на уборку за оборванным прогоном. Модель менять нельзя.
     Чинить тут нечего.

   - **Нет второй попытки — ОСТАЛОСЬ.** Единственная живая часть жалобы.
     Сорвавшаяся проверка сама не повторяется. Обрыв программа замечает —
     `core/lastrun.py` отрабатывает как задумано, при следующем открытии окна
     человеку сказано, что прошлая проверка не доработала, и предложено её
     продолжить, — но новую попытку начинает человек руками. **Эта цепочка
     целая, ломать её не надо.** Решать надо одно: кто повторяет — сама
     программа (не достучалась до Telegram, подождала, попробовала снова) или
     планировщик настройкой «перезапуск при сбое». И как отличить «нет сети»
     от «нечего читать»: во втором случае повтор не нужен. Причина самих
     срывов у автора устранена отдельно (прокси, 24 августа), но механизма
     повтора как не было, так и нет.

5. **Поиск постов в прямом эфире.** Смотреть каналы не по расписанию,
   а прямо сейчас, по ходу. Задача крупная и пока сформулирована одной
   строкой — обсудить, что под этим понимается: постоянно открытое
   подключение к Telegram и показ постов по мере появления, или разовый
   поиск по ключевым словам без пересылки.

## Как у автора всё устроено сейчас

- Программа **установлена** в `D:\софт\Парсер Telegram-каналов`, версия `1.2`,
  данные — в `%LOCALAPPDATA%\TelegramDigest`. Переустановка данные не трогает.
- Батников больше нет в работе: ярлык `run_all.lnk` убран из автозагрузки
  в `всякое другое\` (5 августа 2026). Вернуть — положить обратно
  в папку автозагрузки и убрать приписку из имени.
- Расписание ведёт сама программа, страница «Расписание».
- **Сборочная копия в `dist` и установленная — разные.** `python build.py`
  обновляет только `dist`. Чтобы обновилась установленная: пересобрать
  установщик и поставить поверх.
- **Установка поверх сео-поиск не сносит.** Проверено 5 августа 2026 при
  переходе на `1.2`: `topic_finder` рядом с `.exe` пережил установку.
  Inno Setup затирает свои файлы, а чужие в папке не трогает. Класть
  инструмент заново надо не после каждой установки, а только после удаления
  программы, установки в новую папку и **после пересборки** — вот она папку
  `dist` и правда сносит целиком.

## Что осталось

- Версия (сейчас `1.2`) записана в двух местах: `digest/about.py`
  и `installer.iss`. При смене менять оба.
- Данные сео-поиска переехали, а прежние копии в папке проекта остались
  лежать как страховка: `digest\state.json`, `digest\tg_digest.session`,
  `topic_finder\spheres.json`, `history.json`, `cache\`. Когда доверие
  к новому месту устоится — убрать, чтобы не путались.

## Решения, которые уже приняты (не предлагать заново)

- Рабочий поток со своим циклом asyncio. Не qasync, не QtAsyncio.
- Сборка `--onedir`, не onefile: onefile каждый раз распаковывается и
  раздражает антивирусы.
- Установка в профиль пользователя, без прав администратора.
- Папку установки выбирает человек: страница выбора показывается всегда,
  в том числе при установке поверх старой (`DisableDirPage=no`).
- При удалении данные в `%LOCALAPPDATA%\TelegramDigest` не стираются молча:
  установщик спрашивает отдельно, по умолчанию «нет». Ответ «да» убирает
  и папку данных, и секреты из Диспетчера учётных данных.
- Доставка в приватный канал, не в Избранное.
- Расписание запускает САМО ОКНО программы (`--run-now`), а не отдельную
  тихую проверку: человеку важно видеть ход работы. Плата за это — пока окно
  открыто, следующая проверка по расписанию не начнётся (`app.lock`).
- Задача планировщика описывается через XML, а не ключами `/SC DAILY /ST`:
  только так включается `StartWhenAvailable` — «запустить, как только
  компьютер включат». Без него пропущенное утро пропадает совсем.
- Время и дни хранятся в `settings.json`, планировщик — исполнитель, а не
  память. У него спрашивается только одно: есть задача или нет.
- **LM Studio: убираем за собой, но только своё.** Модель, которая лежала
  в памяти до нас, там и останется; сервер, запущенный человеком, продолжит
  работать. Батник выгружал всё подряд — ему было можно, он запускался
  вручную и в одиночку. Программа может проснуться по расписанию посреди
  чужой работы, и так себя вести не должна.
- Модель поднимается и для тестовой проверки: она точно так же спрашивает
  модель про каждый пост.
- Если в настройках облачный адрес модели, локальный LM Studio не трогаем:
  съел бы память и ничего не дал.
- Если `lms` не нашёлся — не срываем проверку. Возможно, LM Studio открыт
  руками. Не достучимся до модели — об этом скажет сама проверка.
- **Ошибка настроек говорит, куда идти, названиями из окна**: «Поправить:
  «Настройки» → «Доступ к Telegram» → «Куда слать посты»». Имена строк
  в файле (`раздел telegram, поле target`) человеку не говорят ничего — файл
  он не открывает никогда. Поля, которых в окне нет вовсе, названы честно:
  их правят руками в файле, и посылать за ними в окно бессмысленно.
  Строки-адреса живут в `WHERE_*` в `core/settings.py` и меняются вместе
  с подписями в окне настроек.
- **api_id и api_hash показываются на странице входа и только пока не вошли.**
  В «Настройках» они остаются: там их правят, когда всё уже работает.
  Записываются по кнопке «Получить код» и молча при уходе из поля; пустые
  поля сохранённое не затирают. После смены ключей сессия отпускается —
  клиент Telethon создан на прежних и про новые не знает.
- **Оборванная проверка: память освобождаем молча, про саму проверку говорим.**
  Про тестовую тоже говорим, другими словами: терять там нечего. Сначала было
  решено о тестовых молчать — и зря, галочка «Тестовая проверка» стоит по
  умолчанию, так что молчание накрывало почти все обрывы.
- **Название канала запоминает прогон**, в той же записи, что и id
  (`_remember_chan`). Окно тоже пишет туда title — иначе название, найденное
  кнопкой «Проверить все», пропадало бы при следующем открытии страницы.
  Это единственное, что окно пишет в `state.json`.
- **Адрес прокси берём у Windows, своего поля в настройках нет.**
  Telethon в системные настройки не смотрит никогда, поэтому прокси ему
  передаётся параметром при создании клиента — этим занят `core/proxy.py`.
  Адрес спрашивается у самой Windows: тот же, через который у человека уже
  работает обычный Telegram. Своё поле в окне означало бы две настройки
  вместо одной и обязанность следить, чтобы они совпадали. Плата за это:
  отдельной галочки «не использовать прокси» в программе нет — прокси
  выключается там же, где включается, в настройках Windows. Решение
  автора, 24 августа 2026.
- Модель не менять: Qwen3-8B-128K в LM Studio, `/no_think` работает.
- `aiohttp` исключён из сборки: Telethon без него работает, а при импорте он
  строит SSL-контекст из хранилища сертификатов Windows и в сборке падает.
- Сбор затравок для topic_finder — по настройке `digest.extract_seeds`,
  у автора включено, в заготовке для других выключено.
- **Лицензия MIT**, правообладатель `dydrch`. Выбрана вместо GPL: это готовая
  программа для людей, а не библиотека, из которой строят чужие продукты.
  Защищать нечего, а MIT никого не отпугивает лишними обязательствами.
- **В заготовке семь каналов, а не 54.** Личный список автора не должен
  уезжать в публичный репозиторий как «настройки по умолчанию». Оставлены
  крупные русскоязычные: на них новому человеку видно, что программа работает
  и как модель отбирает. В `README.md` прямо сказано, что их можно удалять.
- **`README.md` написан для непрограммиста**, а не для коллеги по цеху:
  порядок разделов повторяет путь человека (что нужно → установка → настройка
  LM Studio → первый запуск), и только в конце блок «Для разработчиков».
  Настройки загрузки модели даны таблицей — их сверяют глазами, а не читают.
  Требование «не меньше 12 ГБ видеопамяти» вынесено в начало раздела: узнать
  об этом после скачивания нескольких гигабайт — обидно.
- **Кнопка «Releases» в `README.md` ведёт по относительному адресу
  `../../releases`.** Так она не знает имени репозитория и переживает
  переименование и перенос.
- **Перед публикацией сверено, что личного в репозитории нет**: `settings.json`,
  `interests.txt`, `state.json`, `run.json`, файл сессии и `CLAUDE.md`
  не отслеживаются, секретов в коде не найдено. Список — тот же, что
  в `.gitignore`; при добавлении новых личных файлов сверять заново.
- **Про непроверенные модели сказано дважды**: в `README.md` и кругляшком «?»
  в настройках (`TIP_MODEL`). Формулировка везде одна и та же по смыслу —
  подставить можно любую, но за отбор постов никто не ручается. Кругляшок
  висит и на «Адрес», и на «Имя модели»: облачную подключают адресом, другую
  локальную — именем, и человек смотрит на то поле, которое правит.

### Сео-поиск

- **Это личный инструмент автора, а не часть продукта.** В установщик он не
  едет: `installer.iss` пакует папку сборки целиком, поэтому `topic_finder`
  там исключён явно — иначе уехал бы к людям.
- **Раздел настроек показывается, только если инструмент лежит рядом с
  программой** (`runner.topics_available()`). У коллег его нет — и раздела они
  не увидят вовсе, вместо того чтобы включить пустое место и потом гадать,
  почему ничего не происходит. Раз галочки может не быть, окно и не трогает
  ключ `find_topics` при сохранении.
- **Внутрь сборки не запекается, лежит обычной папкой снаружи.** Иначе его
  нельзя было бы положить себе и не отдать коллегам. Плата: PyInstaller не
  видит, что инструмент импортирует, поэтому `csv` назван в `hiddenimports`
  руками (`math` и `time` вшиты в интерпретатор, `io` и `re` едут
  в `base_library.zip`).
- **Зовётся синхронно, после закрытия цикла asyncio, до освобождения памяти.**
  После цикла — потому что блокирующий `requests` внутри подвесил бы прогон,
  ровно как с отчётом боту. До освобождения — потому что модель уже в памяти,
  и поднимать её второй раз значит ждать лишние полминуты.
- **Своя обёртка `try`**: упавший сео-поиск не превращается в «проверка
  прервалась». Посты к этому моменту уже разосланы.
- **Режим наследуется у проверки**: тестовая проверка — тестовый сео-поиск.
  Иначе правку было бы не увидеть: галочка «Тестовая проверка» стоит
  по умолчанию.
- **Кнопка «Остановить» сео-поиск не прерывает** — механизма остановки внутри
  нет. Сказано в подсказке под кругляшком «?».
- **Данные — через `paths.topics_dir()`**, рядом с данными дайджеста. Раньше
  лежали рядом со скриптом: пересборка сносила их вместе с папкой, а запуск
  из исходников и из сборки вели два расходящихся набора истории. Переезд
  инструмент делает сам и один раз; то, что уже лежит на новом месте,
  не трогается никогда — иначе старая копия затёрла бы свежую.
- **Сырой вывод в журнале оставлен намеренно.** Строки вида
  `=== topic_finder запущен (режим: dry-run) ===` и `[LLM] кандидатов 25`
  нарушают общее правило «журнал видит пользователь», но сео-поиск включён
  только у автора, и он же единственный этот журнал читает. Решение автора.
- **В репозитории сео-поиска есть свой `.gitignore`** (5 августа 2026):
  `__pycache__/`, `out/`, `cache/`, `history.json`, `spheres.json`. Данные
  давно переехали, но при запуске из старой копии могут завестись и здесь.
  Два хвоста на будущее. Первый: **`spheres.json` уже отслеживается**,
  и строка в `.gitignore` на него не подействует, пока файл не отцепят
  отдельной командой — решено отложить, список направлений, может, и полезно
  хранить в истории. Второй: **править этот файл мне запрещено**. В личном
  `.claude/settings.json` стоят `Edit(./.gitignore)` и `Write(./.gitignore)`
  — они закрывали корневой файл, но ловят это имя на любой глубине.
  Проверено опытом: обычный файл в `topic_finder/` создаётся, `.gitignore`
  — нет. Понадобится правка — или руками, или сузить запрет.

- **Название в окне — «Сео-поиск»**, а не «Темы для статей»: второе описывало
  результат, а не занятие. Ключ настройки остался `digest.find_topics` —
  переименование потребовало бы переноса значения ради ничего.

### Портативный режим у автора выключен

- `settings.json` и `interests.txt` убраны из корня проекта (переименованы
  в `*_ПЕРЕЕХАЛ.*`). Из-за них `paths.home()` выбирал портативный режим,
  и папка проекта жила своей жизнью, а установленная программа — своей.
- Теперь **и батники, и запуск из исходников, и установленная программа**
  работают с одной папкой `%LOCALAPPDATA%\TelegramDigest`. Переустановка
  программы данные не трогает.
- Обратная сторона: если вернуть `settings.json` в корень проекта, портативный
  режим включится снова и программа поедет со старых курсоров. Возвращать имя
  можно только осознанно.

## Грабли, на которые уже наступали

- **Файл сессии Telegram — это SQLite.** Два процесса разом получают
  `database is locked`. Поэтому: окно отпускает сессию на время проверки
  (`release_session`), а второй экземпляр программы не запускается (`app.lock`).
- **`QLabel` в Qt унаследован от `QFrame`.** Стиль `QFrame {...}` разрисовывает
  рамками все подписи внутри. Стили задавать по имени объекта: `#card {...}`.
- **Qt на Windows отдаёт «системным моноширинным» Courier New.** Выбирать
  шрифт явно: Cascadia Mono, Consolas и далее.
- **Цвета нельзя прибивать гвоздями**: тёмно-красный список ошибок пропадал
  на тёмной теме. Все цвета — из палитры, см. `ui.color()`.
- **Тема и размер букв запекаются при сборке виджетов**: после смены окно
  пересобирается целиком (`restart_requested`).
- **Переменная из `except ... as e` удаляется при выходе из блока.** Один раз
  из-за этого падал путь «канал не открылся».
- **`git grep -E` не понимает `\d`.** Аудит секретов молча ничего не находил.
- **Диспетчер учётных данных общий на машину** и про `DIGEST_HOME` не знает:
  в тестах и песочнице подменять имя хранилища через `DIGEST_KEYRING_SERVICE`.
- **Кэш иконок Windows** держит старую иконку для того же пути. Не баг сборки.
- **Безликая иконка на панели задач у НЕустановленной программы — это норма,
  а не поломка.** Иконку для кнопки Windows берёт не у окна: она ищет ярлык
  программы в «Пуске» и берёт картинку оттуда. Запущенной прямо из `dist\`
  такого ярлыка нет, и рисуется стандартный значок «какое-то окно».
  Замерено: значки на окне выставлены оба (малый и большой), иконка внутри
  `.exe` на месте, `icon.ico` в сборке лежит, с нового пути картина та же —
  дело не в них. После установки иконка правильная и с ярлыка, и при прямом
  запуске `.exe` (так её запускает планировщик). Не чинить: чинить нечего.
  Проверять — только на установленной программе.
- **Две копии разом показывают правильную иконку.** Когда в одной кнопке
  несколько окон, Windows берёт значок у окна, а не у ярлыка. Красивый
  симптом, сбивающий с толку: выглядит как «иногда работает».
- `name_self_for_taskbar()` задаёт имя программы для панели задач ДО создания
  QApplication, и та же строка прописана ярлыкам в `installer.iss`. Это НЕ
  лекарство от значка выше — это про другое: чтобы закреплённый ярлык и
  запущенное окно были одной кнопкой, а не двумя.
- **Строки журнала видит пользователь**, а не только разработчик: никакого
  `dry-run`, `state`, `INTERESTING/SKIP` в выводе.
- **Состояние в таблице пишется в прошедшем времени.** «Открывается» было
  результатом проверки, а читалось как процесс: полсотни строк подряд
  выглядели так, будто программа висит. Результат — «открылся», «не открылся»;
  настоящее время оставляем только тому, что и правда идёт: «проверяю...».
- В сборке без консоли `sys.stdout` равен `None`.
- **`lms load` возвращает 1, если модель уже загружена**, и пишет
  `A model with identifier ... already exists`. Это не ошибка. Надёжнее не
  ловить это сообщение, а спросить заранее: `lms ps --json` печатает список
  загруженных моделей в JSON, без разбора человеческого текста.
- **`lms load` рисует крутилку прогресса.** Без чистки управляющих
  последовательностей в журнал человека попадёт каша из служебных символов.
- `lms unload --all` и `lms server stop` можно звать повторно: когда убирать
  нечего, они не ругаются.
- **`schtasks` не принимает XML в UTF-8**: ругается на «неверный формат»,
  и по сообщению догадаться невозможно. Файл описания пишется в UTF-16.
- **Сигнал `clicked` передаёт в обработчик `False`.** У `start_run(confirm=True)`
  этот `False` встал бы на место `confirm`, и настоящая проверка пошла бы
  по кнопке без вопроса. Подключать через `lambda`.
- **Модальное окно в запуске по расписанию — это зависшая задача.** Спросить
  некого: человек мог отойти. Поэтому при `--run-now` нет ни подтверждения
  настоящей проверки, ни сообщения «программа уже запущена».
- **Замок прогона не годится как след «я не доработала».** Его снимает сама
  Windows, когда процесс умер, и по нему не отличить «отработала» от «убили».
  Отсюда `core/lastrun.py`. Закладки по каналам при обрыве целы — они
  двигаются по ходу и остаются на последнем отправленном посте.
- **Галочка «Тестовая проверка» стоит по умолчанию.** Любая правка, которая
  срабатывает только на настоящей проверке, при обычном тестировании не видна
  вовсе. На этом уже обожглись с карточкой оборванного прогона: она работала,
  но не показывалась ни разу.
- **PyInstaller не соберёт, пока программа запущена**: папка `dist\` занята,
  и он падает с `PermissionError` на `base_library.zip`. Проверять успех
  сборки по коду возврата или по метке времени готового `.exe` — трассировка
  PyInstaller не совпадает с шаблоном «ERROR», и провал легко принять за успех.
- **В Telegram программа ходит двумя разными дорогами, и они независимы.**
  Посты — через Telethon по протоколу MTProto, к серверам Telegram. Отчёт
  и файлы — через Bot API, обычным HTTPS на `api.telegram.org`. Одна дорога
  может работать, когда вторая закрыта. Если жалуются «посты пришли,
  а отчёта нет» — смотреть надо именно сюда, а не в настройки бота.
- **Системный прокси Windows видит только одна из этих дорог.** `requests`
  читает его сам и потому отчёт боту уходит; Telethon не читает его
  НИКОГДА, ни на какой платформе. Симптом запутывающий: Telegram на
  компьютере открывается, отчёт приходит, а каналы не читаются совсем,
  и падает всё на первом же шаге, на подключении. Лечится не настройками,
  а параметром `proxy=` при создании клиента, см. `core/proxy.py`.
  Поймали 24 августа 2026: шесть дней проверок подряд упали на этом.
- **Названия каналов есть и в файле сессии Telethon** (таблица `entities`,
  поле `name`), но лезть туда мимо Telethon нельзя: это та же SQLite-база,
  из-за которой ловится `database is locked`.
- **`print()` при пустом `sys.stdout` молча ничего не делает.** Не падает,
  не ругается — просто тишина. В сборке без консоли `sys.stdout` равен `None`,
  и весь вывод сео-поиска (а он пишет только `print`) пропадал целиком:
  инструмент работал полторы минуты и не говорил ни слова. Поэтому `print`
  теперь уходит не в поток, а в сам журнал — и тот раздаёт строку всем,
  включая окно.
- **Журнал может подключить сам себя экраном, и строки задвоятся.**
  `logs.setup` зовётся дважды: при старте окна и на каждую проверку. К моменту
  второго вызова в `sys.stdout` стоит зеркало печати, и поиск потока для
  экрана находил именно его. Дальше запись шла в окно, через зеркало обратно
  в журнал и в окно второй раз; защита loguru от зацикливания обрывала круг —
  отсюда ровно две копии, а не бесконечность. Лечится тем, что своё же
  зеркало потоком не считается (`_console_stream`).
- **Проверка журнала обязана звать `setup` дважды.** Первый тест звал один раз
  и двойные строки не поймал — ломается всё именно на втором вызове.
- **Пересборка сносит `topic_finder` рядом с `.exe`.** PyInstaller удаляет
  папку `dist\Парсер Telegram-каналов` целиком. Пока данные лежали там же,
  каждая сборка убивала историю отданных тем; теперь данные отдельно, но сам
  инструмент класть обратно всё равно надо.
- **Правишь `core/` — обязана быть пересборка.** Инструмент лежит снаружи
  сборки, а ядро внутри: обновишь одно и забудешь другое — снаружи новый код
  зовёт старое ядро. Так и поймали `module 'core.paths' has no attribute
  'topics_dir'`: сборка была на десять минут старше правки. Сверять по времени
  файла `.exe` и исходника — надёжнее, чем по памяти.

## Что в digest.py нельзя ломать

- `is_interesting` зовёт `llm.chat` с `raise_on_error=True`. Ошибка модели
  никогда не превращается в SKIP: курсор остаётся на последнем удачном посте.
- Из ответа модели вырезается `<think>...</think>`.
- `clip_for_filter`: 4000 символов с начала, 1200 с конца. Подобрано под
  контекст 65536, менять только с проверкой.
- Непонятный ответ модели трактуется как интересный (`return True` в конце).
- Ключ состояния канала — ник, а не ссылка (`_chan_key`, `_migrate_key`).
- `_remember_chan` пишет в память по каналам `id`, `key` и `title`. Название
  читать больше неоткуда: канал открыт только здесь и в проверке ссылок.
- `SENT_KEEP` подрезает реестр отправленных, иначе состояние растёт вечно.
- `sys.exit(0)` в конце `__main__`: иначе процесс виснет на `iter_messages`.
- Итоговый отчёт отправляется ПОСЛЕ закрытия цикла asyncio, не внутри `main()`.
- В тестовой проверке состояние читается, но курсоры не используются
  и ничего не пишется.
- Промпт требует от модели ровно `INTERESTING` или `SKIP` — это контракт
  с кодом разбора, его менять нельзя (в отличие от текстов вывода).

## Как проверять

- Настройки читаются: `python -c "from core import settings; print(len(settings.channels()))"`
- Тестовая проверка: `python digest/digest.py --dry-run --hours 2`
- Окно: `python digest/app.py`
- Страница окна, не открывая его: переменная `QT_QPA_PLATFORM=offscreen`.
  Так видно, что страница вообще собирается и что подписи с подсказками
  на месте, — без возни с мышью
- Запуск, как его делает планировщик: `python digest/app.py --run-now`
  (осторожно: проверка настоящая)
- Сборка: `python build.py` (или `--installer` вместе с установщиком). Скрипт
  сам проверяет, что программа закрыта, кладёт сео-поиск рядом с `.exe`
  и сверяет, что сборка новее исходников
- Установщик: `"%LOCALAPPDATA%\Programs\Inno Setup 6\ISCC.exe" installer.iss`
- Вход в Telegram, не трогая боевую сессию: `python digest/sandbox.py`
- Сео-поиск отдельно: `python topic_finder/topic_finder.py --dry-run`

  `.exe` должен быть НОВЕЕ всех изменённых исходников

## Правила работы

- Один шаг — одна проверка. Увидел соседнюю проблему — сказать и ждать.
- Перед каждым шагом — коммит.
- Боевую проверку без `--dry-run` запускает только автор, вручную.
- Секреты в коммиты не попадают. Проверять перед публикацией.
- Ошибся в диагнозе — сказать сразу.
- Считаешь правку бесполезной — так и сказать.
